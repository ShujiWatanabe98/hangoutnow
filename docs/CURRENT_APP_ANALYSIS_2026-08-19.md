# Hangout Now 現行アプリ分析

分析日: 2026-08-19  
分析対象: `7c12c97` 時点  
分析方法: 独立エージェントによるリポジトリ全体の読み取り専用コード監査

## 1. 総評

Hangout Nowは、次の主要体験を一通り実行できる段階です。

```text
Discover → Join → Match → Chat → Hangout → Rating
```

プロフィール、参加条件、正確な位置情報の秘匿、申請と承認、グループトーク、開始・終了、相互評価、1対1トーク、安全管理、通知、説明可能なマッチング、アルゴリズムの版管理、管理画面まで実装されています。

一方、現在の「AI」はルールベースの重み付き推薦です。保存済みの設定項目すべてがスコア計算へ入っているわけではなく、外部KPI、A/Bテスト、管理者認証、ジョブ基盤、モバイル・管理画面テストが次の主要課題です。

## 2. システム構成

| 領域 | 技術・役割 |
|---|---|
| API | NestJS、Prisma、PostgreSQL、JWT、Socket.IO |
| モバイル | Expo SDK 54、React Native 0.81、iOS/Android |
| Web・公開デモ | Node配信のHTML/CSS/JavaScript |
| 管理画面 | Next.js 15 |
| 本番基盤 | Render上のAPI、Web、AdminとPostgreSQL |
| iOS配布 | EAS Build、TestFlight/App Store Connect設定 |

## 3. 実装済み機能

### 認証・プロフィール

- メール登録・ログイン・更新トークン・ログアウト
- 電話番号認証
- LINE、Google、Apple、XのOAuth導線
- 写真最大3枚
- 年齢、性別、自己紹介、活動エリア、興味
- マッチング設定一式
- アカウント削除
- 停止・BANアカウントのアクセス拒否

### Hangout

- 一覧、距離、時間フィルター
- AIスコアによる表示順位
- ハート
- 写真・電話確認済みユーザーによる募集作成
- 参加コメント付き申請
- 年齢・性別条件
- 定員と待機リスト
- 主催者による承認・見送り
- 出欠確認、キャンセル、空席通知
- 開始・終了、自動終了
- 活動履歴

### トーク・評価

- 承認メンバー限定グループトーク
- リアルタイム通知
- Hangout終了後の一度限りの★1〜5評価
- 双方★5の場合だけ1対1トークを解放
- ブロック関係では1対1トークを拒否

### 安全・プライバシー

- ブロックと通報
- 管理者による警告、一時停止、永久停止、復旧
- 措置理由と担当者IDの監査履歴
- 承認前は概略エリアと丸めた位置だけを返却
- 店名、住所、正確な座標、ナビURLは承認後だけ返却
- チャット本文をプッシュ通知へ含めない
- API入力のホワイトリスト検証

### 通知

- アプリ内通知
- 既読、全既読、全削除
- 通知種別の有効・無効
- Socket.IOリアルタイム通知
- Expo Push配信キュー、再試行、Receipt確認
- 無効トークン削除
- 全体緊急停止、テスト通知
- 開催15分前リマインダー

### 管理画面

- 登録ユーザー数
- 24時間、7日、30日のアクティブユーザー
- Hangout・開催完了・評価・通報
- 行動ファネル
- 評価分布
- 不成立理由
- アルゴリズム版別の成立・不成立
- 重みグラフと簡易シミュレーター
- アルゴリズムの下書き、有効化、履歴
- プッシュ通知管理
- 安全管理
- App Store、Google Play、X、Instagramの未連携状態表示

## 4. AIマッチングの評価

### 良い点

- 同意がなければ個別最適化しない
- 行動学習を別途無効化できる
- 重みと判定式を説明できる
- 安全性ペナルティがある
- ブロック関係を候補から除外する
- 版管理とロールバックの基礎がある
- 管理画面から重みを変更できる

### 現状

学習済みMLモデル、生成AI、埋め込み、自然言語理解は使っていません。活動、エリア、時間、人数、年齢、性別、交流スタイル、言語、参加時期、行動履歴、主催者の評価・完了率・会話参加・安全措置を重み付きで計算します。

## 5. 優先課題

### P0: 表示・説明と実装の一致

保存・編集できる次の項目は、現行スコアへまだ直接反映されていません。

- 予算
- 最大移動時間
- 参加目的
- 初参加時の配慮
- 飲酒・喫煙
- 避けたい条件
- 日程の柔軟性

特に「おすすめから優先的に外す」と説明している避けたい条件は、説明どおり計算へ反映する必要があります。

### P0: 管理者認証

現在は共有 `ADMIN_API_TOKEN` と自由入力の担当者IDです。次が必要です。

- 個別管理者アカウント
- MFA
- 権限分離
- セッション失効
- 操作監査

### P1: アルゴリズム評価基盤

- 露出順位ログ
- 順位別CTR
- 参加申請率、承認率、完了率
- キャンセル率、通報率
- バージョンへのユーザー割当
- A/Bテスト
- 公平性・地域偏り監視
- スコアの成立確率への校正

### P1: 管理シミュレーター

現在は主要条件がすべて一致した場合の単純加算です。将来は、匿名化した実データで次を比較する必要があります。

- 旧版と新版のランキング変化
- ユーザー別の影響
- 成立率・完了率・安全指標の推定
- 変更で不利益を受ける集団

### P1: アクティブユーザーの定義

現在は期間内に新しいログインセッションを作った重複なしユーザーです。既存セッションで継続利用したユーザーを捕捉できるよう、認証済みAPI操作の `lastActiveAt` または日次アクティブイベントが必要です。

### P1: 定期処理

プッシュキューとリマインダーはAPIプロセス内のタイマーです。専用ワーカーまたは外部スケジューラへ移し、再起動・複数インスタンス・重複処理へ対応する必要があります。

### P2: 外部データ

- App Store Connectのダウンロード数
- Google Playの獲得ユーザー・インストール数
- Xの公式APIによる関連投稿数
- Instagram Graph APIによるメンション等

外部APIの利用規約、権限、レート制限、保存可能期間を確認し、推測値や無許可スクレイピングは使いません。

### P2: テストと保守性

- モバイルの操作テスト
- 管理画面のコンポーネント・E2Eテスト
- 大きな `App.tsx` の画面分割
- 圧縮された `hangout.service.ts` の整形・責務分割
- 定期処理の統合テスト

### P2: iOS配布の再現性

EAS設定の秘密鍵パスが特定Windows PCに依存しています。EAS Secretなどへ移行し、別PC・CIでも再現できる状態が必要です。

## 6. 推奨ロードマップ

### 直近

1. 保存済み条件をマッチング計算へ追加
2. ユーザー活動日時を正確に記録
3. 管理者認証を個別アカウント化
4. 露出・順位・成果ログを追加
5. 管理画面へ実データ比較を追加

### 公開テスト前

1. 公平性・安全性レビュー
2. モバイルE2Eテスト
3. 通知ワーカー分離
4. App Store Connect指標連携
5. 障害時のロールバック手順整備

### 利用データ蓄積後

1. 現行ルールをベースラインとして固定
2. 統計モデルをオフライン評価
3. 安全条件をハードルールとして維持
4. 小規模A/Bテスト
5. 成立率だけでなく完了率・満足度・安全性を最適化
